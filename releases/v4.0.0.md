# TradeBlocks 4.0.0

**Bring any Option Omega backtest into TradeBlocks in one step, then find out whether it holds up.**

4.0 is released alongside Option Omega's MCP server. TradeBlocks never calls Option Omega: you install both MCP servers in one client, OO's tools read your OO data, and TradeBlocks analyses it as an ordinary block. This is a major version because existing tool inputs, tool output shapes, library exports and stored browser data change; read [Upgrading from 3.x](#upgrading-from-3x) before you upgrade a client, script or library caller.

## Offline book calculations

The public library adds `replayBook` and `searchBookAtDrawdown` without changing
existing exports. Replay compounds whole-contract entries on net closed funds,
with explicit sizing, admission, group reservations and event ordering. Bounded
drawdown-budget search reports feasible best-observed and robust vectors,
near-optimal ranges, reoptimized drop-one searches and seeded entry-cohort
stability. Replay labels closed funds `offline_closed_equity`; optional complete
net open-position marks produce a separate `offline_marked_equity` curve and
drawdown, which search then uses for its risk constraint. Sizing remains based on
closed funds. Missing admitted mark coverage, unusable calibration and infeasible
budgets are refused rather than filled or ranked. See the
[developer guide](../docs/development.md#offline-book-replay-and-drawdown-budget-search)
for required declarations and screening limits.

## Option Omega and TradeBlocks

- **Install both servers.** Install TradeBlocks (`npx tradeblocks-mcp setup`, or the manual configuration in the [MCP server README](../packages/mcp-server/README.md)) and OO's MCP server in the same AI client.
- **Capture (Claude Code).** The optional [`tradeblocks-skills`](https://github.com/tradeblocks-org/tradeblocks-skills) plugin 4.0.0 adds `/tradeblocks:oo-capture`. It saves OO's responses for a saved backtest, a saved portfolio or a run to disk exactly as OO returned them, verifies the complete trade log against OO's own headline count and net profit to the cent, writes `tradelog.csv` and, when OO reports the source's date range, `dailylog.csv` from OO's marked equity curve, and imports them into **one** block with a single `import_csv` call (`dailyLogPath` is new in 4.0). A saved backtest or portfolio always carries that range; a run whose OO headline reports no range is imported with its verified trades only, and the capture says its marked curve is missing. `/tradeblocks:is-this-optimum-real` uses the same capture to test an OO optimizer winner against a stable-region centre.
- **Fallback (every client).** Export the trade log, and optionally the daily log, as CSV from OO and import both with one `import_csv` call:

  ```
  import_csv { "csvPath": "/data/tradelog.csv", "blockName": "My OO Backtest", "dailyLogPath": "/data/dailylog.csv" }
  ```

- **MCP prompts.** Five prompts guide the OO workflows in any MCP client: `bring-in-oo-backtest`, `is-this-optimum-real`, `stress-oo-portfolio`, `live-vs-oo` and `allocate-oo-portfolio`.
- **Supported.** Capture is supported in Claude Code only, with TradeBlocks running locally over stdio. Capture is **not supported** when TradeBlocks runs in Docker or HTTP mode, or in other clients: use the CSV fallback, with the CSVs inside the server's mounted data directory for Docker/HTTP.
- **Verified against OO staging.** Capture was verified on OO's staging MCP server with its 2026-09-29 tool schemas: a saved backtest of 191 trades, a saved portfolio of 237 trades with three members, and a scratch run of 24 trades reconcile to OO's headline count and net profit to the cent. It has not been re-verified against OO's production MCP server.

## `import_csv` takes an optional daily log

`import_csv` accepts an optional `dailyLogPath` beside a trade log's `csvPath`, so one block holds the trades and the account's marked daily curve (for OO, its daily log). A daily log pairs only with a trade log, not with a reporting log or another daily log. Both files must be readable by the server: local paths for stdio, or paths inside the mounted data directory for Docker/HTTP. Omit `dailyLogPath` for a trade log alone. Both files are checked before the block is created: if either is refused, no block is created. The result reports the daily log's `recordCount` and calendar `dateRange` under `dailyLog`.

## Upgrading from 3.x

Each item below is detailed in its section further down.

- **Tools refuse arguments they do not declare.** A call carrying an undeclared top-level argument now fails instead of silently dropping it.
- **`TradeBlocksPlugin` tools must use `registerTool` with a Zod object `inputSchema`.** A plugin tool registered with a raw shape, a union, no schema, or the SDK's legacy `server.tool()` now stops the server at startup, naming the tool.
- **Trade dates are calendar `YYYY-MM-DD` strings in tool output** (`list_blocks`, `get_block_info`, `get_reporting_log_stats`, `get_statistics` peak exposure, `run_walk_forward`, `get_tail_risk`, `run_sql` DATE columns, and `import_csv` `dateRange`). Parse them as calendar dates, not timestamps.
- **`import_csv` refuses rows it cannot load** (impossible dates, missing or unparseable P/L or daily-log values) instead of creating a block that fails later or loading zeros.
- **Trade `Premium` is dollars per contract**, and reporting `Initial Premium` is a per-share quote. `Trade.premiumPrecision` is removed.
- **Results change** for same-curve Calmar, starting capital without `Funds at Close`, `toReported` live-vs-backtest comparisons, OO's own `P/L %`, and trade-based Sharpe/Sortino east of UTC.
- **Library exports removed or reshaped** in `@tradeblocks/lib` and `tradeblocks-mcp/test-exports`.
- **The web app migrates browser storage once** (IndexedDB 5 → 6 → 7) and recalculates cached charts.
- **Security.** Upgrading picks up the patched dependencies below; the MCP SDK range floor is now `^1.31.0`, so an install cannot resolve an SDK affected by GHSA-6qxp-vccf-f47h.

## Option Omega workflows

### MCP prompts for Option Omega workflows

The MCP server offers prompts for the Option Omega workflows in stdio and HTTP: the four below, and `allocate-oo-portfolio` (see _OO portfolio allocation-loop MCP prompt_). In Claude Code, with the server configured as `tradeblocks`, they appear in the `/` menu as `/tradeblocks:<prompt> (MCP)` and run when typed as `/mcp__tradeblocks__<prompt>`:

- `bring-in-oo-backtest`: bring a saved OO backtest's trades into a TradeBlocks block.
- `is-this-optimum-real`: with the plugin, guide two separately verified OO scratch runs into one trade-only comparison block under distinct strategies; test both arms and their paired best-minus-centre difference, stating its selection and overlap limits.
- `stress-oo-portfolio`: stress a portfolio's trade log as a block.
- `live-vs-oo`: compare live trades from a reporting log with an OO reference backtest's block, using the existing `compare_backtest_to_actual`, `analyze_discrepancies`, `analyze_slippage_trends` and `analyze_live_alignment` tools. The reporting-log CSV goes in the same block folder as the OO trade log; the prompt names the OO reference (a scratch run's `runId`, or a saved backtest's ID and capture date).

With the optional `tradeblocks-skills` plugin, the import prompt uses `/tradeblocks:oo-capture` and the optimum prompt points to `/tradeblocks:is-this-optimum-real`. Without it, users export each run's CSV from OO into a separate block at a server-readable path; only tests against zero run, not a paired difference. The prompts do not transcribe OO data through the model or call OO from TradeBlocks. Server instructions explain the division of work and block/SQL discovery. MCP initialize reports the installed `tradeblocks-mcp` package version rather than a stale hard-coded version.

### OO prompts take arguments, name the right OO tools and import the daily log

- The four Option Omega prompts take optional arguments: `bring-in-oo-backtest` and `stress-oo-portfolio` take `ooId` and `block`, `is-this-optimum-real` takes `optimizationId`, and `live-vs-oo` takes `block`. In Claude Code they follow the command, for example `/mcp__tradeblocks__bring-in-oo-backtest <savedBacktestId> my-strategy`. Calls without arguments, including a `prompts/get` with no `arguments` field, render the prompts as before.
- `bring-in-oo-backtest` and `stress-oo-portfolio` quote a saved backtest's or portfolio's OO headline figures from `get_saved_backtest` or `get_saved_portfolio`, and use `get_backtest_results` or `get_portfolio_results` only with a finished run's `runId`. An `ooId` is tried as a saved ID first.
- Without the `tradeblocks-skills` plugin, `bring-in-oo-backtest` asks for OO's daily-log export as well as the trade log and imports both with one `import_csv` call using `dailyLogPath`, so the block carries OO's marked daily curve. With only a trade log it says the block has no OO marked daily curve.

### OO portfolio allocation-loop MCP prompt

- `allocate-oo-portfolio` is a new stdio and HTTP MCP prompt. It proposes allocations from a TradeBlocks block with distinct OO portfolio member strategies, then checks each candidate against shared starting funds via OO `run_portfolio`, `get_portfolio_status` and `get_portfolio_results`. It never changes the saved portfolio; saving a candidate requires an explicit request and a new portfolio.
- Where the installed `oo-capture` describes saved-portfolio capture, it can supply the saved portfolio's strategy-labelled trades and whole-book daily curve; older plugin versions capture only saved backtests and runs. Elsewhere, OO's CSV export plus `import_csv` works, with optional `dailyLogPath`. Trade-derived counterfactuals and OO's marked-equity headline figures remain separately labelled.
- `stress-oo-portfolio` no longer says portfolio capture is unavailable; it uses that capture under the same condition and keeps the CSV path.

`allocate-oo-portfolio` takes optional `ooId` (a saved portfolio ID or a run's `runId`) and `block` arguments.

### OO capture reads Option Omega's 2026-09-29 trade-log table

- The optional `tradeblocks-skills` `oo-capture` plugin works again on Option Omega's 2026-09-29 MCP schema, verified against OO staging (a saved backtest of 191 trades, a saved portfolio of 237 trades with three members, and a scratch run of 24 trades reconcile to OO's headline count and net profit to the cent). OO's `get_trade_log` now returns a `tradeColumns` header plus `trades` rows instead of `items` objects. Before the plugin change, capture saved the pages but verification refused `INVALID_PAGE` on every OO source, so `bring-in-oo-backtest`, `is-this-optimum-real`, `stress-oo-portfolio`, `live-vs-oo` and `allocate-oo-portfolio` could not bring in a fresh OO capture. The capture reads each row by its column name, refuses a column it does not recognise (`UNKNOWN_COLUMN`) or a missing required column (`MISSING_COLUMN`) by name, and its page-by-page hook message now reports source, sort, offset, row count, total and `nextOffset`.
- The `Legs` cell of a captured trade log changes format. It used to be `<side> <contracts> <expiry> <strike> <type> @ <price>` joined by `; `, built from per-contract leg prices that OO no longer sends. It is now OO's own leg text, for example `1 Feb 6 5850 P STO 2.45 | 1 Feb 6 5840 P BTO 1.20`: the text OO's CSV export writes and the form the `replay_trade` leg-string parser reads, so a captured log now replays like an OO CSV import. Leg prices in that text are OO's per-share quotes, not per-contract dollars; leg deltas are no longer provided by OO and are not reconstructed.
- Capture verification is otherwise unchanged: complete paging in one fixed ascending sort, count and net profit to the cent (book and every portfolio member), `isIgnored` trades excluded, `profit` net of fees with no second deduction, OO's `profitPercentage` as `P/L %` (blank when OO's cell is null).

This is a plugin change; the TradeBlocks server needs none for it.

### Trade P/L % uses Option Omega's own value

**Behaviour change to trade `plPct` for CSVs carrying a `P/L %` column.** When a trade log has Option Omega's `P/L %` column and a trade's cell is numeric (`97.905…` means 97.9%), that value is now the trade's `plPct` in the Report Builder, What-If explorers, threshold analysis and the MCP report tools (`get_field_statistics`, `find_predictive_fields` and `filter_curve`). Before, the web importer ignored the column and the MCP server kept it only as the custom field `P/L %`; both recomputed `plPct` as P/L ÷ |Premium × No. of Contracts| × 100. The column stays optional: without it, or for a blank or unparseable cell, `plPct` is that same computed value, and `import_csv` never refuses a row because of it. The `premiumEfficiency` alias follows `plPct`. In the web app's combined leg groups mode, a single-row group keeps OO's value; a multi-row group has no OO value for the combined position and computes combined P/L ÷ |combined premium × contracts| × 100. `netPlPct` is still computed from net P/L, so on a row where OO's cell differs from the recomputation, `plPct` and `netPlPct` differ even though both are on the same net basis; that gap is not a fee effect. MCP trade logs still expose the raw column as `custom.P/L %`. Existing browser blocks keep their computed values until the source CSV is re-imported; MCP folder blocks read the column on their next load.

**Library consumers:** `@tradeblocks/lib`'s `Trade` gains an optional `plPct?: number`. It is the source-reported value and is `undefined` when the CSV has no numeric `P/L %` cell. `EnrichedTrade.plPct` remains the resolved value: the source's cell when present, otherwise the computation above.

### MCP help and tool references name real tools

`import_csv`'s `nextSteps` now point to registered tools (`get_block_info`, `run_sql`, `run_monte_carlo`) instead of `get_block_details`, `get_trades` and `run_analysis`, which the server does not provide. The VIX-context hint now names `fetch_bars` or `import_market_csv`, then `enrich_market_data` and `compute_vix_context`, instead of the removed `import_from_api`. `import_csv`'s description no longer says it needs local filesystem access: its paths must be readable by the server, locally for stdio or inside the mounted data directory for Docker/HTTP.

`tradeblocks-mcp --help` now says that `install-skills`, `uninstall-skills` and `check-skills` print the tradeblocks-skills plugin installation instructions and exit, which is what they have done since skills moved to the plugin; it no longer lists `--platform` or `--force`. The commands themselves are unchanged.

The MCP Tools Reference lists every registered tool, the CSV-format documentation describes `plBasis` (default `net_includes_fees` for Option Omega exports), the required columns and dollar-form premiums, and the Usage Guide gains a section on bringing in an Option Omega backtest.

### Guided safe local MCP setup

Adds `tradeblocks-mcp setup` for Claude Desktop, Claude Code, Codex CLI and Gemini CLI. People select a client/data folder and explicitly approve the preview; agents use `--client`, `--folder`, `--yes` and `--json` for one structured result without prompts. A conflicting `tradeblocks` entry needs separate `--replace` permission. Equivalent entries are not rewritten and are still verified.

Human mode uses readable prose and a numbered client picker with detection markers, accepting either a number or name without auto-selection. Machine JSON remains exclusive to `--json`. Verification allows a bounded 120 seconds for a first npx launch downloading the package and native DuckDB binaries; its preview/progress explains that possibility. Bootstrap runtime guidance follows the package's declared engine.

Setup uses official user-scope CLI registration commands or Desktop's documented per-OS JSON file. It refuses malformed/unreadable settings, preserves unrelated settings and existing environment secrets, and shows environment key names rather than values. Desktop updates are atomic and retain a backup; Claude Code replacement keeps a backup and restores it on a failed remove/add. The registered npx path is absolute, and fresh Desktop entries include Node/npm's PATH so GUI launches do not depend on a shell startup file.

Success requires a real MCP initialization and tool discovery against the read-back configured server subprocess, with a bounded timeout and shutdown. This is not a claim that the AI client connected: Desktop must be reopened and CLI clients need a new session. Verification failure is distinct from registration failure and returns non-zero even if configuration was written.

The packaged bin now enters through a small engine-checking bootstrap, before loading setup or the existing server module. This lets unsupported Node versions return actionable prerequisite guidance rather than failing while importing newer built-ins. The existing `server/index.js` server/host entry remains available.

Node/npm/client installation remains manual, with prerequisites documented for macOS, Windows and Linux before any npm command. No OO credentials, provider keys or optional Claude Code skills plugin are needed. Existing stdio/HTTP invocation, environment options and retained skills-instruction commands are unchanged.

Review hardening: equivalent registrations reject extra launch/settings fields;
Codex read-back accepts only its precise null/default metadata. Gemini replacement
refuses env values its CLI would truncate. Every existing client config is backed
up before registration and restored on command failure or read-back mismatch.
Successful vendor CLI rewrites may still normalize unrelated settings; the backup
retains the original bytes. Early refusals do not suggest restarting a client or
claim verification ran. Source CLI processes retain orphan-lock recovery.

## Breaking changes: interfaces and stored data

### Tools and prompts refuse arguments they do not declare

**Behaviour change to the input contract of every MCP tool and prompt.** Before this change, a tool dropped any top-level argument it did not declare and ran as if the argument had never been sent. It now refuses the call: `Input validation error: Invalid arguments for tool <name>: Unrecognized keys: "a", "b"`. The error names every undeclared key, and the tool does not run. For example, `import_csv` refuses an option it does not have and creates no block. Each tool's `tools/list` input schema now sets `additionalProperties: false`. Any of the five workflow prompts likewise refuses an argument it does not declare. Omitted and empty prompt arguments still render the prompt.

Callers that send only declared arguments are unaffected. A client or script that used to send extra keys, even harmless ones, now gets this error and should send only the arguments in the running server's schema. The main aim is to make version skew visible, for example a newer `tradeblocks-skills` plugin sending an option to an older server. This protects only 4.0 and later servers. A 3.x server still drops unknown arguments, so the plugin keeps checking the running server's schema before it relies on an option such as `dailyLogPath`.

Only top-level arguments are checked. A nested value keeps its own rules, such as the free-form `keyMetrics` of `profile_strategy`. A `TradeBlocksPlugin` tool must be registered with `registerTool` and a Zod object `inputSchema`, which the server makes strict. A plugin tool registered with a raw shape, a union or no schema is refused at startup, naming the tool. So is one registered through the SDK's legacy `server.tool()`. A schema replaced later through the handle's `update({ paramsSchema })` is not made strict.

### Every MCP tool reports trade dates as calendar dates

**Behaviour change to existing MCP tool output.** Trade-calendar dates in tool output are now calendar dates as `YYYY-MM-DD`, for example `{ "start": "2024-01-02", "end": "2024-03-28" }`. This covers a trade's opened or closed day, a daily-log day, and any range or window built from them. The day is the same on every server timezone. `import_csv`'s `dateRange` makes the same change (see the next section). These tools changed shape:

- `list_blocks`: `blocks[].dateRange.start` and `.end` were `2024-01-02T00:00:00.000Z`.
- `get_block_info`: `dateRange.start` and `.end` were ISO timestamps of the server's local midnight, such as `2024-01-02T06:00:00.000Z`. On a server east of UTC they named the day before the date in the file (local 2024-01-02 in UTC+14 became `2024-01-01T10:00:00.000Z`).
- `get_reporting_log_stats`: `dateRange.start` and `.end`, the same way as `get_block_info`.
- `get_statistics`: `peakExposure.byDollars.date` and `peakExposure.byPercent.date` were ISO timestamps of the server's local midnight, with the same previous-day error east of UTC.
- `run_walk_forward`: `periods[]` and `skippedWindows[]` `inSampleStart`, `inSampleEnd`, `outOfSampleStart` and `outOfSampleEnd` were `2024-01-02T00:00:00.000Z`.
- `get_tail_risk`: `dateRange.start` and `.end` were ISO timestamps, and named the previous day east of UTC.
- `run_sql`: DATE columns, such as `trades.trade_data.date_opened` and `date_closed`, were returned as objects like `{ "days": 19724 }`.

These tools kept the `YYYY-MM-DD` shape but reported the wrong day on some servers. On a server east of UTC, `paired_bootstrap_comparison` reported `overlapWindow` one day early. On the same servers, `get_statistics` reported `calculationMethodology.returns.dateRange` one day early, `marginal_contribution` did the same for `calculationMethodology.baseline.returns.dateRange`, and `what_if_scaling` did the same for the `returns.dateRange` of each methodology arm. On a server that observes daylight saving time, such as America/Los_Angeles, `analyze_walk_forward_degradation` could label `periods[].window` and `skippedWindows[]` dates one day early once a window crossed the autumn clock change, and select its trades by those days. `analyze_edge_decay` showed the same windows in `signals.walkForward.detail.periods`.

**Numbers that change on servers east of UTC.** When a Sharpe or Sortino ratio is computed from trades rather than a daily log, each trade's P/L used to be attributed to the previous calendar day. That moved returns onto weekends and changed the risk-free rate day. Those ratios now use the trade's own day, and `returns.observations` no longer includes the weekend days that the shifted day key created. The tools that report trade-based Sharpe or Sortino include `get_statistics`, `compare_blocks`, `block_diff`, `marginal_contribution`, `what_if_scaling`, `run_walk_forward`, `analyze_period_metrics`, `analyze_rolling_metrics`, `analyze_walk_forward_degradation` and `analyze_edge_decay`. `get_statistics` `peakExposure.byDollars.exposurePercent` and `peakExposure.byPercent.exposurePercent` now divide by the same day's equity instead of the next day's. The web app's trade-based Sharpe and Sortino ratios get the same correction on computers east of UTC.

**Numbers that change on servers that observe daylight saving time, including US timezones.** Once a window crosses the autumn clock change, `analyze_walk_forward_degradation` and `analyze_edge_decay` now select each window's trades by the correct calendar days. Their per-window in-sample and out-of-sample trade counts can therefore change. So can the per-window Sharpe, profit-factor and win-rate efficiencies, the efficiency-trend slope, intercept and p-value, both tools' `recentVsHistorical.recentAvgEfficiency`, and `analyze_edge_decay` `summary.wfAvgEfficiency`. A server in UTC gets the same numbers as before.

**Library exports.** In `tradeblocks-mcp/test-exports`, `listBlocks()` and `BlockInfo.dateRange` now return `YYYY-MM-DD` strings rather than `Date` values. `buildBlockTradingDayIndex`, `armHoldingPeriods` and `buildArmDaySeries` now read a `Date`'s local calendar day, matching how the loader holds trade dates. Before, they read its UTC day, so a caller that passes UTC-midnight `Date` values on a server west of UTC now gets the previous day.

Clients that parse these fields as timestamps should read them as calendar dates instead. Real instants are unchanged: `calculatedAt`, sync times and market-feed timestamps are still ISO timestamps. Inputs and stored block files stay the same.

### `import_csv` reports its date range as calendar dates

**Behaviour change to existing `import_csv` output.** For every CSV type (`tradelog`, `dailylog`, `reportinglog`), the result's `dateRange.start` and `dateRange.end` are now the file's first and last calendar dates as `YYYY-MM-DD`, for example `{ "start": "2024-01-02", "end": "2024-03-28" }`. Previously they were ISO timestamps such as `2024-01-02T06:00:00.000Z`. That timestamp came from the server's local midnight, so on a server east of UTC it could name the day before the date in the file (local 2024-01-02 in UTC+14 became `2024-01-01T10:00:00.000Z`).

Clients that parse `dateRange` as a timestamp should read it as a calendar date instead. The new paired `dailyLog.dateRange` uses the same calendar form. The next section, on `import_csv` refusals, describes the stricter input acceptance and receipt corrections; imports with no convertible rows are now refused rather than returning a null range.

### `import_csv` refuses unloadable CSV rows

**Behaviour change to existing `import_csv` input acceptance.** Trade logs and reporting logs now refuse an impossible opened/closed calendar date or missing/unparseable P/L; gross-before-fees trade rows also require parseable opening and closing commissions. A daily log with a missing or unparseable value refuses the whole import. Errors identify the CSV file line (including the header), and no block is created, even for a paired import. Previously an impossible date could create a block that failed to sync, while invalid P/L or daily-log values could silently become zero.

Reporting-log headers are checked the same way the loader reads them. A `PL` column is now accepted as `P/L` and loads. Before, the header check refused it even though the loader reads it. A reporting log whose only date or P/L headers are `date_opened` or `pl` is now refused as missing `Date Opened` or `P/L`. Before, those headers passed the check but loaded no trades (`date_opened`) or loaded every P/L as zero (`pl`).

A date with a time or timezone suffix, such as `2024-01-02T00:00:00Z`, now loads on the calendar day it names, both in imports and in folder-discovered blocks. Previously the loader read it as an instant, so a server west of UTC stored the trade on the day before. `import_csv` accepts or refuses such a date the same way in every server timezone. For a TAT reporting row, the check applies to the date the loader actually uses: an impossible `OpenDate` is refused even when the row's `Date` is valid. Previously the loader rolled such a date into the next month.

`Portfolio Value`, `Value` and `Equity` daily-log columns now load as net liquidity in imported and folder-discovered blocks. Folder loading skips daily-log rows without a parseable value rather than fabricating zero; folder-discovered trade acceptance and DuckDB sync row counts are unchanged. Successful receipts count actually loaded trades and use the block ID, rather than the display name, when a trade has no Strategy. Valid Option Omega exports continue to import without a provider key.

### Trade Premium is dollars per contract

**Behaviour change to trade-log imports and analytics.** `Premium` is dollars for one contract (one lot), regardless of whether its CSV cell contains a decimal point: `250` and `250.00` both mean $250 per lot. Position premium is the absolute per-contract value multiplied by the contract count. Option Omega's EMA row with $420 premium and three contracts has $1,260 total premium and $1,251 net P/L, or 99.2857% premium efficiency, independently of margin. A padded `.00` OO premium no longer inflates efficiency through a guessed option multiplier. MFE/MAE dollar excursions use the same total-premium basis.

**Existing CSV authors:** a per-share quote such as `2.50` in the old examples must be written as `250` for a $250-per-lot premium. Leaving `2.50` makes MFE/MAE dollar amounts 100× smaller and a computed premium efficiency 100× larger (a trade whose CSV carries OO's own `P/L %` keeps that value). Trade-log `Premium` is distinct from reporting-log `Initial Premium`; the Trading Calendar shows backtest premiums as an explicitly labeled $/share quote to compare with OO reporting quotes, without changing the stored dollar premium. Programmatic callers must remove `Trade.premiumPrecision`; the field is no longer accepted by the model or validator.

Existing browser blocks migrate their stored trades once on upgrade, preserving the premium amounts they displayed before the change; old `premiumPrecision` markers are removed. Re-importing the source CSV applies the new dollars-per-contract contract instead. Cached combined-trades, enriched-trades and performance-snapshot calculations are deleted by the upgrade and recalculated on use (see _Stored browser blocks keep their calendar days_).

### Reporting Initial Premium is a per-share quote

**Behaviour change to reporting-log imports and Trading Calendar analytics.** `ReportingTrade.initialPremium` and DuckDB `trades.reporting_data.initial_premium` mean the signed opening price in dollars per share of one contract (credit positive, debit negative), distinct from trade-log `Trade.premium` in dollars per contract. Option Omega's `Initial Premium` already uses the quote and is imported verbatim. TAT's `TotalPremium` is position dollars; import divides it by `Qty × 100` (for example, −$26,550 / 5 / 100 = −$53.10/share, matching `PriceOpen`). MCP folder blocks resync their reporting rows from source CSVs after the parse-version change; SQL readers should multiply `abs(initial_premium) × 100 × num_contracts` for opening position premium dollars.

Actual Calendar Premium Capture divides reported P/L by those position premium dollars. The EMA row with $1,251 P/L, $4.20/share and three contracts is 99.2857%; the TAT example with $1,929.35 P/L on $26,550 opening debit is 7.2669%. Per-contract scaling leaves the reported quote unchanged, and strategy premium totals now represent signed position dollars. Negative capture is not clamped. A row with a zero initial premium has no usable denominator, so the aggregate it belongs to shows Premium Capture as unavailable rather than averaging the remaining rows.

Existing browser reporting rows with no trustworthy unit are not silently interpreted as quotes: their Premium Capture is unavailable (`-`), including legacy TAT rows formerly stored in dollars per spread. For the same reason, `StrategyDayComparison.actual.totalPremium` from `aggregateTradesByStrategy` is now `number | null`, and is null when any row in that strategy has an unknown premium unit. Already-imported OO rows whose retained raw `Initial Premium` cell matches the stored value have recorded quote provenance and remain available. Re-importing a legacy CSV stamps the confirmed quote unit.

The same stamp makes its actual Premium Capture and strategy premium total available.

### Daily exposure names calendar days

**Library export shape change.** In `@tradeblocks/lib`, `calculateDailyExposure` now returns calendar days as `YYYY-MM-DD`, for example `"2024-01-02"`. This changes the meaning of these strings:

- `DailyExposurePoint.date`, in `dailyExposure[]`.
- `PeakExposure.date`, for both `peakDailyExposure` and `peakDailyExposurePercent`.

They were ISO instants of the server's local midnight, such as `2024-01-02T00:00:00.000Z` in UTC or `2024-01-01T10:00:00.000Z` in UTC+14. A caller that parsed them as timestamps should now treat them as calendar days: compare the strings directly, or split them into year, month and day. Do not pass them to `new Date(...)`, which reads `2024-01-02` as UTC midnight, the evening of January 1 west of UTC. The type stays `string`. This library change adds no MCP output change beyond the calendar-date change above, which covers `get_statistics` `peakExposure` dates; `get_performance_charts` `daily_exposure` keeps its shape.

**Equity lookup.** `calculateDailyExposure` and `calculateExposureAtTradeOpen` now read each `equityCurve` point's `date` as a `YYYY-MM-DD` calendar day, which is what both the MCP tools and the web performance snapshot pass (see _Web performance charts name calendar days_ below). When several points share a day, the last one is that day's equity. They used to take the first ten characters of the date's UTC text. **A caller that passes an ISO timestamp** (for example `"2024-01-02T00:00:00.000Z"`) no longer matches any day, so its exposure % comes out zero. Pass `YYYY-MM-DD` instead.

**Numbers that change on computers east of UTC, and on the web app.** On a computer east of UTC, an equity point at local midnight has a UTC date one day earlier, so each exposure day used the previous day's equity. The web app's Daily Exposure chart percentages and the `exposureOnOpen` percentages on enriched trades now divide by the same day's equity. In America/Los_Angeles, the snapshot's opening equity point (one second before the first close) sat on the wrong day, so the first exposure day could use the wrong equity there too. A computer in UTC gets the same numbers as before.

### Web performance charts name calendar days

**Library export shape change.** In `@tradeblocks/lib`, `buildPerformanceSnapshot` and `processChartData` now return every trade and daily-log day in `SnapshotChartData` as a calendar day, `YYYY-MM-DD`. This changes the meaning of these strings:

- `equityCurve[].date` and `drawdownData[].date`.
- `returnDistributionDetails[].date`, `tradeSequence[].date`, `romTimeline[].date`, `rollingMetrics[].date`, `volatilityRegimes[].date`, `premiumEfficiency[].date` and `marginUtilization[].date`: the day the trade opened.
- `holdingPeriods[].dateOpened` and `holdingPeriods[].dateClosed`. `durationHours` is unchanged.

The same change applies to these other exports:

- `GroupedLegEntry.dateOpened`, from `deriveGroupedLegOutcomes` (the performance store's `groupedLegOutcomes`).
- `MarginTimeline.dates`, from `buildMarginTimeline`.
- `calculateDailyReturns()[].date`.
- The keys of `groupTradesByEntry` and `groupReportingTradesByEntry`, and so `GroupedLegEntry.id`, start with the calendar day, as in `2025-01-03|10:15:00|MEIC`.
- In the web chart exports, the MFE/MAE `Date` CSV column and the JSON `mfe-mae-scatter` `date` field, and the Assistant JSON export's `trades[].dateOpened`.

They were ISO timestamps of the computer's local midnight. On a computer in UTC+14, such as `Pacific/Kiritimati`, a trade opened on 2025-01-03 came out as `2025-01-02T10:00:00.000Z`, and the web charts plotted it on 2025-01-02. It now comes out as `2025-01-03` in every timezone. In UTC it was `2025-01-03T00:00:00.000Z`. The type stays `string`.

**How to read them.** Treat these values as calendar days: compare the strings directly, or split them into year, month and day. Do not pass them to `new Date("YYYY-MM-DD")`, which reads the day as UTC midnight, the evening before west of UTC. To get a local `Date`, use `parseISO` from `date-fns` or `new Date(year, month - 1, day)`.

**Equity curve.** Points used to carry synthetic timestamps a few seconds apart so that no two were equal. Each point is now dated by its trade's close day, so trades that close on the same day share a date. Point order, `tradeNumber`, `equity` and `highWaterMark` are unchanged, and no point is merged. The opening balance is dated the day before the first close. A block with open trades only dates its points by open day. A block with no trades has one point dated today. `calculateDailyExposure` and `calculateExposureAtTradeOpen` now read equity curve dates only as `YYYY-MM-DD` (see _Daily exposure names calendar days_ above).

**Numbers that change on the web app east of UTC.** The drawdown chart now keeps one end-of-day point per calendar day. On computers east or west of UTC, the opening balance used to fall on the same UTC day as the first close and was merged into it. The Margin Utilization table puts each trade in its opening month; before, a trade opened on the first of a month fell in the previous month east of UTC. The Trading Calendar's Sharpe, Sortino, max drawdown, CAGR and Calmar from a daily log now use exactly the logs dated inside the selected range. East of UTC, they used to drop the first day and add the day after the range. The Position Sizing margin chart dates each day by its calendar day.

**Numbers that change on computers in UTC+0 with summer time.** In `Europe/London`, `Europe/Dublin` or `Europe/Lisbon`, the Sunday when summer time begins and the Monday after it used to share one day key. Without a daily log, `PortfolioStatsCalculator` now counts them as two days. So do the MCP tools that report its `maxDrawdown` and `avgDailyPl`, such as `get_statistics`. That also applies to Monte Carlo daily resampling (`run_monte_carlo` with `resampleMethod: "daily"`) and to leg grouping. Each case needs trades on that Sunday. Other timezones get the same numbers as before, and no MCP tool output changes shape.

**Web cache.** The performance snapshot cache in IndexedDB is now stored under `performance_snapshot_v4_<blockId>`. The browser storage upgrade deletes snapshots cached by an earlier release, and the block's chart data is recalculated with calendar days on the next visit.

### Stored browser blocks keep their calendar days

**Browser storage migration (IndexedDB version 6 → 7).** The web app now stores trade, daily-log and reporting-log dates, a block's date range and the dated rows in its cached calculations as `YYYY-MM-DD` calendar days, not as moments in time tied to the timezone they were imported in. A block imported in one timezone and opened in another (after travel or on a new computer) now shows every trade, daily-log and reporting row on its original day in the Trading Calendar, the performance charts, the trade log, filters and exports.

The first time the updated app opens, it upgrades every existing block once. It works from each stored date: dates imported in a timezone less than 10 hours behind UTC or less than 12 hours ahead of it, and dates written by older versions at UTC midnight, are converted to their exact original day. Option Omega strategy-log (reporting) rows write their dates with a time of day; rows imported since v3.2.0 kept the original cells, so when a saved cell has no time zone its day is taken from it exactly, in any timezone. Three kinds of date cannot be confirmed from what is stored:

- dates imported 10 to 12 hours behind UTC (as in Hawaii and American Samoa) or 12 to 14 hours ahead of it (as in New Zealand, Fiji, Tonga and Kiritimati), because one stored moment names a different day on each side of the date line;
- dates stored with a time of day that is not on a quarter hour, rather than as a whole day — including strategy-log rows imported before v3.2.0, which kept no original cells;
- strategy-log dates whose saved cell carries a time zone (or the time `24:00`): these are always flagged, whatever time they show.

Those dates keep the day the browser showed before the update, so none of them moves without notice. The block list and every analysis page for that block show a prompt naming the file(s) involved and how many dates could not be confirmed; they may be off by one day. Importing that file again (Edit block → replace the file) fixes the dates and clears the prompt for it. New imports are never flagged. One limit remains: a date that was imported with a time of day exactly on a quarter hour (for example `2025-01-02 14:00`) cannot be told apart from a whole day, so it is converted as one and may move by one day without a prompt. Option Omega backtest trade logs carry whole days and are not affected.

What users may see after the update: legacy rows that older versions stored at UTC midnight used to display a day early in browsers west of UTC (for example the Americas); they now show their true day. The Trading Calendar's Equity Curve Comparison chart now plots each trade on its calendar day; east of UTC it used to plot every point one day early. The Report Builder's date axes (for example P/L % Over Time) plot calendar days for the same reason. The library's `computeDerivedFields().dayOfWeek` (reached through `calculateCumulativeDistribution` and the regime-breakdown helpers) now reads the local calendar weekday; east of UTC it used to name the previous weekday. No current web or MCP result changes, because neither calls those helpers. Cached charts and statistics are rebuilt from the upgraded data on first use. The upgrade cannot start while another tab is still running the previous version: close or reload the other TradeBlocks tabs if the app waits on first load. If the upgrade fails it leaves the stored data untouched and is retried on the next load. CSV imports and the library's in-memory `Date` fields are unchanged.

## Changed results

### Same-curve Calmar ratio

**Behaviour change to existing `calmarRatio` output.** For unfiltered blocks with a daily log, Calmar now divides CAGR measured from the first to last daily `netLiquidity` over the log's own span by the daily log's maximum absolute `drawdownPct`. Previously it divided trade-based CAGR by daily-log drawdown, mixing two curves. The statistics output now includes `calculationMethodology.calmar.basis`: `daily_log_marked_curve` for these blocks and `realized_trade_equity` for trade-only or strategy/ticker-filtered results.

`compare_blocks` reports the new value too, and each compared block now carries an additive `calmarBasis` with the same two values whenever `calmarRatio` is among the requested metrics. Sorting by `calmarRatio` still orders by the value itself, so a block with a daily log (marked Calmar) and a trade-only block (trade Calmar) can appear in one ranking, each labelled with its basis.

This repair leaves trade-only and filtered Calmar unchanged, except for one fix that applies to both bases: a CAGR of exactly zero with a positive drawdown now gives a Calmar of `0`. Before, Calmar was unavailable in that case. It does not itself change the meaning or value of `cagr` or `maxDrawdown`; the starting-capital and calendar-date changes in this release can change them (see those sections). If a CAGR cannot be computed (for a marked curve: fewer than two rows, no span, or non-positive net liquidity), or if drawdown is zero, Calmar is unavailable. It is never replaced by a ratio mixing two curves.

### Evidenced MCP starting capital

**Behaviour change to existing `get_statistics.stats.initialCapital`.** For a trade CSV without `Funds at Close`, it is now a positive starting balance rather than a negative or zero inference from the loader's placeholder. On an unfiltered block with a usable daily log, the start remains first-day `netLiquidity - dailyPl`; otherwise the two MCP tools use an explicitly assumed $100,000. A real numeric zero after a first-trade loss is still an observed balance, not a missing field. An impossible (nonpositive or non-finite) daily-derived start falls back to a positive observed trade-funds start if available, then to the labelled $100,000 assumption. This repair leaves other funded blocks' capital, daily-log statistics and trade-realized chart behavior as they were (other 4.0 changes, such as calendar-day keys, can still move them); this includes paired logs omitting P/L, whose legacy daily P/L is zero. Fee-aware net P/L still deducts fees once according to the declared P/L basis.

For unfunded blocks, reconstructed trade balances now feed the calculator before it computes capital-dependent figures. Trade-based `cagr`, trade-equity `maxDrawdown`, and trade-based `calmarRatio` can therefore change alongside `initialCapital`; previously an impossible starting balance could suppress CAGR and corrupt drawdown. With a usable daily log, the daily-derived start feeds trade CAGR, while daily-log drawdown and marked Calmar retain their distinct documented bases. A daily row that cannot certify a starting balance — P/L missing on an unfunded block, or a nonpositive derived start — only loses the right to set `initialCapital`; the daily log still drives Sharpe, Sortino, drawdown, time in drawdown and marked Calmar exactly as before.

`get_statistics.calculationMethodology.initialCapital.source` and `get_performance_charts.equityCurveCapitalSource` are additive fields with values `observed_trade_funds`, `daily_log`, or `assumed_default`. Every `get_performance_charts` view seeded from starting capital — equity curve, drawdown, margin utilization, exposure and `monthly_returns_percent` — uses that one start, so an unfunded block with a daily log now reports monthly percentages against the daily-derived start instead of $100,000. The equity curve remains trade-realized, not the daily log's marked account equity. The MCP subset-equity rebuild now also starts missing-funds subsets at the assumed amount; independent Monte Carlo, health, period segmentation, drawdown attribution, browser snapshots and the public calculator's other readers retain their existing capital inference. The library's exported realized equity curve and monthly-percent builders accept an optional explicit starting amount for the MCP chart; callers omitting it retain their previous calculation.

### Live-vs-backtest comparisons scale each figure once

Two corrections to the live-versus-backtest comparisons under `scaling: "toReported"`. Both change existing output values.

**Behaviour change to `analyze_live_alignment` (and `analyzeLiveAlignment` in `@tradeblocks/lib`).** Under `toReported`, the per-strategy `backtestPerContract` and `perContractGap` scaled the backtest P/L twice. They took the backtest P/L already scaled to the reported contract count and divided it again by the backtest contract count. Each per-contract figure is now that side's own P/L divided by its own contract count, so it is the same in every scaling mode. For example, a $1,000 backtest trade on 10 contracts matched to a $190 live trade on 2 contracts now reports $100 backtest per contract, $95 actual per contract, and a gap of −$5. Previously it reported $20 backtest per contract and a gap of +$75. `efficiency`, direction agreement, the totals, and the `raw` and `perContract` outputs are unchanged.

**Behaviour change to `compare_backtest_to_actual`.** Under `toReported` with `matchedOnly: false`, `summary.totalBacktestPl`, `totalActualPl`, `totalSlippage` and `avgSlippagePercent` are now computed from matched rows only, which is what `matchedOnly: true` already did. Previously these totals added unmatched backtest rows at their own contract size to matched rows scaled to the reported size, and added unmatched live P/L to the actual side. As a result, `totalSlippage` mixed two scales and was not execution slippage.

Unmatched rows still appear in `comparisons` and `groups`, and their P/L is still reported separately in `summary.unmatchedBacktestPl`, `summary.unmatchedActualPl` and `unmatchedSummary`, each row at its own contract size. The summary `note` and the tool description state this basis. `groups[].totalSlippage` and `avgSlippage` already covered only matched rows and are unchanged. Under `raw` and `perContract`, every row shares one scale, and totals with `matchedOnly: false` still include unmatched rows as before.

These two scaling repairs change no inputs, no other tools and nothing in the web app.

## Market data and library

### Market enrichment memory and history repair

**Fix for `enrich_market_data` and `refresh_market_data` running out of memory** (tradeblocks#482, #401). Each enrichment call used to load every ticker's published enriched partitions into a temporary working table, and backfill it from all of `market.spot_daily`, even when only one ticker was requested. With one Parquet file per ticker and session, that load grew with the whole market library. At about 25,000 enriched slices it exhausted DuckDB's default cap on a 16 GB machine (`11.1 GiB/11.1 GiB used`), on the first call after a restart and for a single ticker. Enrichment now loads only the requested ticker's slices; the no-SpotStore fallback additionally loads SPX's published return for VIX trend, while cross-ticker VIX context still reads its own spot history. The tool inputs and outputs are unchanged, and so is the default memory limit.

**Unbounded `enrich_market_data` now fills missing older sessions.** Before, a one-day `refresh_market_data` advanced the ticker's enrichment watermark, and a later `enrich_market_data` then wrote only sessions after it, so older unpublished sessions stayed missing from `market.enriched`. An unbounded call now reads the ticker's full daily spot history and publishes every session not yet enriched. When repairing history behind a watermark, Tier 3 reads intraday bars only for sessions being published, rather than loading every minute bar across the full history. A failed publication still leaves the watermark unchanged, so a retry can succeed.

### Published risk-free rates

TradeBlocks now publishes the full DTB3 and SOFR FRED histories every day as `rates.json` on a separate `rates-data` branch. This replaces the weekly workflow that tried to commit Treasury rates to `master`, which had stopped working, and it covers SOFR for the first time.

**Web app**

- Reads the published file by default and caches the last validated copy in IndexedDB.
- Shows the effective DTB3 date next to Sharpe and Sortino.
- The Fetch published risk-free rates switch turns this off.
- Offline users fall back to the cached file or the bundled rates.
- CSV import and the library's bundled rate lookups work without an API key or network access.

**MCP server and market-data refresh**

- Use the same validated rates, with a local disk cache.
- Newer canonical rate slices become available, and unchanged historical slices keep their content identities.
- `TRADEBLOCKS_PUBLISHED_RATES=off` keeps the MCP server on the bundled rates.

**Releases**

- The release gate checks that neither bundled history is more than ten calendar days behind the published file.
- The reviewed `node scripts/rates.mjs seed` command refreshes both tables before a release.

**Bundled rates**

- The bundled DTB3 history runs through October 6, 2026, and SOFR through October 7, 2026.
- The DTB3 bundle corrects two misdated January 2026 observations: 2026-01-03 is now 2026-01-05, and 2026-01-10 is now 2026-01-12, with the same values. Weekend lookups for January 10 and 11, 2026 now use the January 9 rate (3.52%) instead of 3.56%, and the January 5 and January 12 rate slices change identity.

**CLI**

- `node scripts/rates.mjs check --json` reports `current`, `behind`, or `unknown`, independently of release gating.

### Inclusive point-in-time spot reads

**Additive programmatic API.** `SpotStore.readBars(ticker, from, to, upperEt?)` now accepts an optional inclusive upper Eastern timestamp on the final day, in `YYYY-MM-DDTHH:mm` form. Both canonical Parquet and DuckDB reads apply the date/time predicate in SQL before rows materialize in JavaScript, rather than loading later observations and filtering them afterward.

For example, `readBars("SPX", "2025-01-06", "2025-01-08", "2025-01-08T10:30")` retains complete earlier days and final-day observations up to and including `10:30`. The bound must match the final date; invalid clock values, UTC suffixes, offsets and mismatched dates refuse even without data. The same interface covers VIX and other spot tickers.

Existing three-argument calls and full-session daily aggregation are unchanged. No provider credentials or network calls are introduced. See [Market Data](../docs/market-data.md#point-in-time-spot-store-reads).

### The provenance entry exports early-close sessions

**Additive programmatic API.** `tradeblocks-mcp/market/provenance` now also exports `isEarlyCloseSession(date)`, beside `isXnysSessionDate` and `enumerateXnysSessions`. It answers `true` for an XNYS session that closes early (13:00 ET) and `false` for a full session or a non-session day. The caller passes an Eastern calendar date as `YYYY-MM-DD`. A date outside the calendar's supported range (`XNYS_SESSION_CALENDAR_SUPPORTED_FROM` through `XNYS_SESSION_CALENDAR_SUPPORTED_THROUGH`) throws `RangeError`, the same as the other calendar functions. Existing exports and behaviour are unchanged.

### Provenance stores stop syncing every ancestor directory on each write

`ContentObjectStore` and `FilePartitionCommitStore` (`tradeblocks-mcp/market/provenance`) previously fsynced every directory from the target up to `/`, and each one's parent, on every write. Each store instance now syncs a directory, together with its parent's entry for it, when it creates the directory or first meets it, and skips it on later writes while the path still names the same directory (device, inode and birth time). A directory that is removed and recreated is synced again. On a filesystem that reports no birth time, directories are synced on every write, as before.

What is durable when a write returns is unchanged: the written object, its containing directory, and the entry of every directory on its path. The stores' constructors, methods, results and stored bytes are unchanged. Provenance writes issue far fewer fsyncs, so refresh and publication time depend less on how long the disk takes to flush.

### OO replay attribution

The public `@tradeblocks/lib` calculation entrypoints now include an additive, pure OO replay-attribution module. Given raw Option Omega trades, its dated book curve and an injected option-quote lookup, it values open legs at the requested close, reconciles daily per-strategy contributions to the book, and reports drawdowns, episodes, quote evidence and unavailable days. Existing calculation exports and MCP `replay_trade` pricing are unchanged. The method prefers SPXW quotes over SPX even for third-Friday expiries when both are present, as measured against the Option Omega book. Its recorded root-precedence map also defaults to RUTW before RUT and NDXP before NDX (registry-derived, not measured against OO), with per-underlying caller overrides; other underlyings use their own root. The map is recorded alongside mark time, fee factor and tolerance.

Missing, non-positive, crossed or over-10× quotes are recorded as missing observations with reasons rather than priced; usable quotes use their raw mid, without forward-fill or an HL2 fallback. This recorded validity rule derives from the MCP replay's positive-side and anomalous-spread checks, while leaving that replay unchanged. Days following a non-positive prior net liquidity are unavailable because the fractional tolerance has no positive base. Dollar drawdown episodes remain defined across zero and are ordered by depth rounded to cents, then earlier peak date.

Strategy costs are required for direct `cumulativeReplayTradeMark(trade, date, quoteLookup, cost, parameters?, markTime?)` calls and supplied by the strategy cost schedule for daily attribution. Exit slippage uses the trade's aggregate package contract count; if that field is absent, replay derives the count only when all leg counts agree. Mixed-ratio positions without an aggregate count are unavailable by strategy name rather than assigned an ambiguous exit cost.

The replay method is `oo-replay-method/v2`. Open positions are marked one minute before the equity session close (12:59 ET on an early close, 15:59 ET otherwise). The bounded XNYS session calendar (`xnys-full-day-2022-2030-v1`) also supports market-data provenance and spot-session coverage. The recorded method parameters include `mark_rule` and `calendar_revision`, and every quote observation cites its actual `mark_time`. Days outside the supported calendar range are unavailable rather than silently marked at 15:59.

The repository's unpublished `@tradeblocks/lib` package owns the XNYS rules. `tools/generate-replay-calendar.mjs` emits bounded membership snapshots for the separately published MCP package, Node spot-session tool, and Python resident; regenerate and review them together when the calendar revision changes.

### Quote reads can skip Greek columns

**Additive programmatic API.** `QuoteStore.readQuotes` and `QuoteStore.readQuotesBulk` accept an optional fourth argument, `neededGreeks`. Omitted, the query is unchanged. `[]` reads no Greek, IV or Greek/rate provenance column, leaving typed nulls in their place; a non-empty list reads only those Greeks with their provenance. Quote-only readers save memory and read time. The test helper `quoteParquetGreekProjection(cols, alias, [])` now also emits typed nulls for the provenance columns.

### Computed option Greeks are documented

[Market Data](../docs/market-data.md) now declares the method behind cached Greeks labelled `greeks_source = 'computed'`: each written revision with its rate, dividend yield and provenance fields, the inputs, the Black-Scholes/Bachelier threshold (`dte >= 0.1` uses Black-Scholes), the implied-volatility solve and output units. It also documents stored rows labelled `tbill_3mo` for gamma that TradeBlocks did not write. No code, schema or output changes.
