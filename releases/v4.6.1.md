# TradeBlocks 4.6.1

**When a trade has no ticker, market-joined tools now warn that they assumed SPX instead of doing it silently. This affects non-SPX blocks captured with the `oo-capture` plugin 4.0.0, which never wrote the trade's underlying.**

4.6.1 is a patch release. It adds a warning to existing outputs and changes no tool input, default or credential. Thanks to Amy in the Discord for the report and the TSLA repro.

## What was wrong

TradeBlocks reads each trade's ticker from an `Underlying`, `Ticker` or `Symbol` column. When a trade had none of these, TradeBlocks assumed SPX and gave no warning. The `oo-capture` skill in the tradeblocks-skills plugin 4.0.0 read Option Omega's per-trade `underlying` but never wrote it to `tradelog.csv`. So a captured TSLA or GLD backtest imported as SPX.

P&L, fees, trade counts and strategies were correct. Anything joined to market data was matched against SPX instead: VIX, regime, enrichment, market fields used by filter analysis, and the market-data tools.

**Who is affected:** blocks imported from an `oo-capture` capture of a non-SPX backtest or portfolio, and any other CSV of non-SPX trades without a ticker column. SPX blocks are unaffected.

## Behavior changes

### Missing trade tickers are an explicit SPX assumption

Market-joined tools now return a warning when a trade has no usable ticker and its market context falls back to SPX. The warning:

- names the assumption;
- counts affected trades (not unique ticker/date keys);
- asks for an `Underlying` or supported ticker column.

It appears even when SPX data exists and the join succeeds. Existing warnings are retained; the portfolio health check uses its existing warning flags.

We warn rather than refuse because native Option Omega CSV exports can omit the ticker column, and refusal would break existing public users of those exports. This is an additive output change with no tool input schema change, no new configuration, and no provider credential requirement. Explicit SPX and TSLA trades do not produce the warning. Trade P&L, fee basis, counts and strategies are unchanged.

`Underlying` already imports by header name on both the loaded-trade and synced-ticker paths. A producer-shaped TSLA capture now has an import regression covering both.

## Repairing an existing capture

Upgrading TradeBlocks does not repair a block that was already imported: the trade's underlying was never in its CSV, and TradeBlocks cannot infer it. Repair it with the tradeblocks-skills plugin 4.0.1, which writes an `Underlying` column:

1. Update the plugin to 4.0.1.
2. Re-run `oo-capture`'s `verify` on the saved capture, using the same `--strategy` if you chose one. This regenerates `tradelog.csv` from the saved Option Omega responses.
3. Import the new `tradelog.csv` as a new block, check that market-joined tools no longer warn about SPX, then delete the old block.

If the capture directory was deleted, capture the backtest or portfolio again. For a hand-made CSV, add an `Underlying` column with each trade's verified underlying and re-import.

## Compatibility

- No tool input, default ticker, setting or credential changes. Warning fields are absent when unused, so existing response shapes are preserved.
- Dependency updates: `express-rate-limit` ^8.7.2 in `tradeblocks-mcp`, plus development and web-app dependency bumps.
