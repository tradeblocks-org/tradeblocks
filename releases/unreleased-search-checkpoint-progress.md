# Unreleased — Search progress and checkpoint resume

The public `@tradeblocks/lib` `searchBookAtDrawdown(input, options?)` calculation accepts optional `onProgress`, `checkpoint`, `resumeFrom` and `feasibleId` controls. Progress reports completed evaluations, coordinate/robust phase, auxiliary scope, best-so-far within that scope and a lazy `checkpoint()` function. Calling it returns a detached JSON snapshot of that event's committed prefix. Journal copying occurs only when the caller captures a checkpoint or receives the final plain `result.checkpoint`, not on every progress event. Callers can persist every N evaluations or on their own elapsed-time cadence.

Version-2 caller-owned checkpoints journal compact metrics and feasibility verdicts across coordinate, robust, drop-one and seeded stability/sensitivity searches; prepared weights, economic keys and rounded-to-zero lists are reconstructed rather than stored in successful entries. No full replay results or filesystem access are added. Resume checks a canonical identity over the entire economic request and caller constraint identity, then reconstructs deterministic search control flow without repeating saved replay or feasibility evaluations. Consumed missing-mark outcomes remain named errors, never invented metrics. Completed checkpoints reuse all outcomes. A changed request is refused with `search_checkpoint_identity_mismatch`. A feasibility policy requires the same opaque `feasibleId` at save and resume; resuming without it is refused with `search_checkpoint_constraint_identity`. Callers must retain the same deterministic policy: changing its implementation without changing its ID reuses saved verdicts.

When `input.feasible` is supplied, checkpoint-capable calls (`checkpoint: true`, `onProgress`, or `resumeFrom`) require `feasibleId` before any evaluation or progress event; otherwise they throw `search_checkpoint_constraint_identity` instead of producing an unresumable save. Calls without these controls remain unchanged. Identity retains replay trade-array order and binds whether a feasibility policy is present, so reordering trades or adding/removing the policy refuses resume.

A throwing progress observer aborts with `search_progress_callback` and the original exception as `cause`. Save `event.checkpoint()` first; it contains the committed evaluation. Best-so-far and captured snapshots are detached from live state. Opt-in controls add `result.checkpoint`; omitted controls preserve the existing serialized result, evaluation order, budgets, defaults and economic semantics. Journal storage grows linearly; snapshot copying is proportional to the saved prefix, so saving every evaluation still costs quadratic total copying. Resume reconstructs coordinate control flow and bootstrap cohorts. MCP tools, replay behavior and provider requirements are unchanged.
