# Unreleased — Search progress and checkpoint resume

The public `@tradeblocks/lib` `searchBookAtDrawdown(input, options?)` calculation accepts optional `onProgress`, `checkpoint`, `resumeFrom` and `feasibleId` controls. Progress reports completed evaluations, coordinate/robust phase, auxiliary scope, best-so-far within that scope and a detached JSON checkpoint. Caller-owned checkpoints journal metrics and feasibility verdicts across coordinate, robust, drop-one and seeded stability/sensitivity searches; no full replay results or filesystem access are added.

Resume checks a canonical identity over the entire economic request and caller constraint identity, then reconstructs deterministic search control flow without repeating saved replay or feasibility evaluations. Consumed missing-mark outcomes remain named errors, never invented metrics. Completed checkpoints reuse all outcomes. A changed request is refused with `search_checkpoint_identity_mismatch`. A feasibility policy requires the same opaque `feasibleId` at save and resume; resuming without it is refused with `search_checkpoint_constraint_identity`. Callers must retain the same deterministic policy: changing its implementation without changing its ID reuses saved verdicts.

A throwing progress observer aborts with `search_progress_callback` and the original exception as `cause`. Save the event's checkpoint first; it contains the committed evaluation. Events are detached from live state. Opt-in controls add `result.checkpoint`; omitted controls preserve the existing serialized result, evaluation order, budgets, defaults and economic semantics. Checkpoint capture copies the growing journal, and resume reconstructs coordinate control flow and bootstrap cohorts. MCP tools, replay behavior and provider requirements are unchanged.
