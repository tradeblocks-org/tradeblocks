# Unreleased — trade P/L % uses Option Omega's own value

**Behaviour change to trade `plPct` for CSVs carrying a `P/L %` column.** When a trade log has Option Omega's `P/L %` column and a trade's cell is numeric (`97.905…` means 97.9%), that value is now the trade's `plPct` in the Report Builder, What-If explorers, threshold analysis and the MCP report tools (`get_field_statistics`, `find_predictive_fields` and `filter_curve`). Before, the web importer ignored the column and the MCP server kept it only as the custom field `P/L %`; both recomputed `plPct` as P/L ÷ |Premium × No. of Contracts| × 100. The column stays optional: without it, or for a blank or unparseable cell, `plPct` is that same computed value, and `import_csv` never refuses a row because of it. The `premiumEfficiency` alias follows `plPct`. `netPlPct` is still computed from net P/L, so on a row where OO's cell differs from the recomputation, `plPct` and `netPlPct` differ even though both are on the same net basis; that gap is not a fee effect. MCP trade logs still expose the raw column as `custom.P/L %`. Existing browser blocks keep their computed values until the source CSV is re-imported; MCP folder blocks read the column on their next load. Web backups from `exportTradesToCSV` now include the `P/L %` column.

**Library consumers:** `@tradeblocks/lib`'s `Trade` gains an optional `plPct?: number`. It is the source-reported value and is `undefined` when the CSV has no numeric `P/L %` cell. `EnrichedTrade.plPct` remains the resolved value: the source's cell when present, otherwise the computation above.

This note does not bump a version or publish a release.
