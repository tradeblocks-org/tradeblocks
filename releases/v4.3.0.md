# TradeBlocks 4.3.0

**Use your own daily datasets with clearer baselines, session-aware freshness and filter suggestions ranked by P&L.**

4.3 follows contributor feedback on daily-dataset analysis: make covered and uncovered trades explicit, distinguish a weekend from a missed observation, and suggest exclusions that improve total P&L rather than win rate alone. It builds on the dataset tools introduced in 4.1 without changing user values or canonical market data. Existing `suggest_filters` calls can return different suggestions and rankings; read [Behavior changes](#behavior-changes) before comparing new output with a saved report.

## Behavior changes

### `suggest_filters` defaults to a P&L objective

`objective` now defaults to `"totalPl"` on both the default market path and the optional `fields` path. Standalone suggestions and default-path composites are admitted only when their kept trades improve total P&L over their covered comparison pool. They rank by P&L improvement (`plDelta`), with win-rate gain (`winRateDelta`) breaking ties. A suggestion must both keep and remove trades.

Select `objective: "winRate"` for win-rate admission/ranking, with P&L improvement as the tie-breaker. This selects the win-rate objective, not an exact reproduction of every older result: composite projections and support semantics also change below. The fields path still returns no composite suggestions; the default market path returns up to ten standalone suggestions and five composites drawn from pairs of the top standalone suggestions.

Responses name `objective`, `rankingRule` and the support interpretation. Each standalone/composite suggestion adds `tradesKept`, `keptFraction`, `tradesRemoved` and `objective`, so the population supporting its result is visible.

### `minImprovementPct` is ignored under `totalPl`

`minImprovementPct` remains a win-rate gain threshold in **percentage points**, defaulting to 3 under `winRate`. Under `totalPl` it is ignored; it is not a P&L percentage threshold. The response includes an explanatory note when the argument was supplied.

`minImprovementThreshold` is now **null under `totalPl`**, including the new default, rather than always a number. Under `winRate` it reports the configured/default win-rate threshold. Clients must handle the nullable field.

### `confidence` means sample-size support

The retained `confidence` key describes **sample-size support, not statistical confidence**. Both paths and default-path composites use the same rule:

- **High:** at least 20 trades kept and 10 removed.
- **Medium:** at least 10 kept and 5 removed, when the high threshold is not met.
- **Low:** otherwise.

Keeping **less than 20%** of the covered pool always caps support at low and adds a `Low retention` warning. Exactly 20% is not below the cap. On the fields path, this replaces the former kept-only thresholds of 100 trades for high and 30 for medium. Support labels can therefore change even for the same cohort.

### Composite projections describe kept trades

Default-path composites exclude trades satisfying **both** component skip conditions; their projected win rate and average P&L now describe the **kept complement**, not the excluded intersection. `tradesAffected` remains the number excluded. Composites use the selected objective for admission and ranking, just like standalone suggestions. The old separate requirement for a greater-than-two-percentage-point gain over the stronger standalone is removed; the previous five-excluded-trade gate is also replaced by the shared nonempty-kept/nonempty-removed admission and support rule.

**Composite `improvement` keeps its meaning:** composite kept-trade win rate minus the better standalone kept-trade win rate, in percentage points, with both standalones evaluated on the composite's same covered pool. It is neither P&L improvement nor the composite's gain over the unfiltered pool. `winRateDelta` and `plDelta` report those baseline-relative gains separately. Because `improvement` no longer gates admission, an admitted composite can have a small or negative `improvement` while meeting the selected objective.

### Close-column metadata and nullable age summaries

Import/list/catalog field metadata now reports `knownBy: null` for close columns; open columns retain the dataset's configured value. This corrects the display of column timing without changing matching.

Dataset calendar-day `medianAgeDays` and `maxAgeDays` are null when no attachments are accepted. Session diagnostics include rejected candidate attachments, while calendar-day statistics and `attachments` describe accepted values only. Clients consuming age summaries should handle those nulls and the new diagnostic fields below.

## Covered dataset baselines

Field-based `suggest_filters` retains all-trade `currentStats` and adds `fieldBaselines` keyed by field, with covered `count`/`totalPl` and `uncoveredCount`/`uncoveredTotalPl`. `comparisonPopulation: "fieldBaselines"` explicitly identifies the population against which each suggestion is measured.

`filter_curve.baseline` adds the same uncovered count and P&L alongside its covered population. This makes the two tools' baselines directly comparable without treating missing field values as filtered-out observations. Freshness refusals count as uncovered for that field.

## Session-aware dataset freshness

Dataset age now includes **missed expected XNYS sessions**, computed from the source row selected by the shared causal resolver, not by a second matcher or a weekday approximation:

- Close columns expect the prior session: Friday close to Monday entry is zero missed sessions; a missing Friday is one. Holidays do not count.
- Open columns expect today's source only at or after the declared known-by time in Eastern Time; before then, the prior session is expected.
- Timestamped observations remain as-of. For the daily-session diagnostic, an open column without a known-by time uses midnight ET; this does not infer an intraday publication cadence.

Existing calendar-day ages remain. `datasetAge` additionally reports `sessionAgeStatus`, `medianAgeSessions`, `maxAgeSessions`, `staleAttachments` (candidates missing at least one expected session), `unsupportedSessionAge` and `rejectedAttachments`. Session summaries include refused candidates; calendar-day summaries count accepted attachments only. `datasetWarnings` names stale, unsupported and refused fields with counts.

The existing XNYS calendar is bounded to **2022–2030**. Ages outside its supported range are explicitly `unsupported`, not guessed. Undeclared legacy timing is also unsupported; in practice this applies to legacy web datasets, since MCP imports always declare timing.

### Opt-in `maxMissedSessions`

An optional nonnegative integer `maxMissedSessions` is available on `enrich_trades`, `suggest_filters`, `analyze_regime_performance`, `filter_curve`, `find_predictive_fields`, `get_field_statistics`, `analyze_structure_fit` and `validate_entry_filters`.

A supplied limit refuses a dataset attachment when its missed-session age exceeds that limit, or its age is unsupported. Refused values count as uncovered in that field's analysis population. `enrich_trades` includes session age in accepted provenance and identifies refused fields/provenance in `datasetRejections`. Aggregate diagnostics retain rejected candidates so a refusal does not hide its reason.

Omit the limit to preserve unlimited causal carry-forward and the existing matching behavior. Built-in market fields are unaffected. The shared library's `resolveDatasetColumnAtTime` accepts the optional limit and returns `sessionAge` plus `accepted` alongside the selected value, source row and availability timestamp.

## Dataset CSV paths in Docker

The [MCP server README](../packages/mcp-server/README.md#market-data-tools) and [tool reference](../docs/mcp-tools.md#market-analysis) now show the host/container distinction. With the default `-v ./data:/data` mount, put a CSV at `./data/datasets/vrp.csv` on the host and pass `csvPath: "datasets/vrp.csv"` or `"/data/datasets/vrp.csv"` to `import_daily_dataset`. Use a container path beneath the configured data root, not the host path. Data-root containment is unchanged.
