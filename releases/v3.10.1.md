# Tradeblocks 3.10.1

## The server no longer shuts down another copy of itself

If your client starts more than one copy of the MCP server against the same data
directory, you may have seen it disconnect a second or two after every startup,
over and over. Claude Desktop does start more than one copy — one for the desktop
app, and another for Cowork and Code sessions — so this could repeat for weeks:

```
Server started and connected successfully
Message from client: method="initialize"
Server disconnected
Recovered DuckDB lock ... by stopping force-recovery tradeblocks-mcp process
```

The analytics database allows one writer at a time. Each copy took the write lock
briefly at startup to create its tables, and a copy that found the lock already
taken **stopped the process holding it** — which was the other working copy. Your
client then restarted the copy that had just been shut down, and that restart shut
down the one that had survived. Nothing was ever wrong with your data or your
configuration.

Occasionally the survivor failed too, reporting `Failed to initialize DuckDB ...
after lock recovery`, because a third copy still held the lock and the startup only
cleared one.

Startup now waits for another copy to finish instead of stopping it. Any number of
copies can read the database at the same time, so the second one to start simply
joins as a reader and you will see a line saying so. Nothing is lost by joining as
a reader: the first write operation takes the lock and creates anything missing.

Two things worth knowing:

- **A copy that is genuinely abandoned is still cleaned up.** A server whose
  launcher has exited shuts itself down within a couple of seconds on its own, and
  a startup will still clear one that has been left behind.

- **Stopping a live copy is now something you ask for.** If a copy has wedged and
  is holding the database indefinitely, set `DUCKDB_LOCK_RECOVERY` to `true` in the
  server's environment for one run. Leave it unset otherwise — the copy holding the
  database is normally somebody's working session.

You can also set `DUCKDB_OPEN_WAIT_MS` to change how long startup waits for another
copy before giving up. The default is 15 seconds.

## A writing tool can still be blocked by another copy that is only reading

This is not new, but it now explains itself instead of leaving you guessing. A tool
that writes — a data import, a market refresh, a sync — needs the whole database to
itself, and it cannot get that while another copy has it open for reading, even an
idle one. The tool retries for a few seconds and then tells you another server holds
the database. Close or idle the other session and run it again.

[Getting Started](../docs/getting-started.md) now has a section on running more than
one copy of the server.
